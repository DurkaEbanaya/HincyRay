# DNS при белых списках Билайн LTE

## Правило диагностики для этого подключения

По указанию пользователя результат **Google FAIL** в карточке «Доступность
Direct» (`directAvailabilityCard`) следует считать рабочим признаком включённых
белых списков. Одновременные VK/ya.ru OK помогают отличить этот режим от общего
обрыва связи. Это соглашение для диагностики данного подключения, а не
универсальное доказательство фильтрации или новая автоматическая настройка.

В этом режиме:

- локальный DNS и разрешение адресов VPN-серверов — через Keenetic
  `192.168.1.1`;
- не полагаться на прямой доступ к `1.1.1.1`, `8.8.8.8` и внешнему DoH;
- удалённый DoH, если используется, направлять явно через VPN;
- перед использованием DNS роутера проверять, что запросы от Mihomo получают
  реальные адреса и не возвращаются в собственный fake-IP listener.

## Подтверждённая неисправность и исправление 2026-10-03

Основной DNS и fallback использовали `https://1.1.1.1/dns-query` без явно
выбранного VPN. Прямой доступ к нему через LTE не проходил. Ранние IP-CIDR
условия Vivox вызывали разрешение адреса до выбора последующих DIRECT/VPN
правил, поэтому новые подключения ждали стандартный пятисекундный DNS-таймаут.
Настроенный DIRECT DNS не устранял ожидание на этапе выбора правила.

Изолированный REDIRECT A/B подтвердил причину: Wildberries Seller с исходным
DNS отвечал за 5,3–5,5 с, с тем же DoH через `#proxy` — за 0,78 с. Аналогичная
проверка HTTPS корня сервера провайдера OpenCode: 5,66 → 1,09 с. Код HTTP404
корня использован только как свидетельство завершённого HTTPS, а не успешной
авторизованной работы модели.

По разрешению пользователя применены через `POST /api/dns` и обычный
`POST /api/routing/apply`:

```json
{
  "local_servers": ["192.168.1.1"],
  "remote_servers": ["https://1.1.1.1/dns-query#proxy"]
}
```

Временное ядро предварительно подтвердило эту комбинацию и отсутствие петли.
Обычное применение закрыло текущие соединения Mihomo и восстановило работу
ядра/firewall. Проверены неизменные сохранённые профили, подписки, активный
профиль, пользовательские правила, device routes, split routing, Mihomo features,
Dead Servers и избранное. Приложение и бинарник не менялись.

### Проверки после применения

Три последовательных HTTPS-запроса с ПК:

| Ресурс | Ответ | Полное время |
|---|---|---|
| Wildberries Seller | 200 | 0,20–0,41 с |
| Ozon Seller | 307 | 0,12–0,24 с |
| Сервер провайдера OpenCode A6API, корень | 404 | 0,82–1,07 с |
| Сервер провайдера OpenCode Ludka, корень | 302 | 0,38–0,57 с |

Новые неавторизованные браузерные контексты:

- Wildberries: HTTP200, DOM 0,526 с вместо 10,463 с; 98 запросов, без сетевых
  ошибок и завершённых запросов дольше 1,5 с за окно наблюдения.
- OpenCode public site: HTTP200, DOM 0,851 с вместо 5,691 с; без сетевых ошибок.
- Ozon: HTTP403 сохранился в автоматическом браузере, DOM 0,531 с вместо
  6,334 с. Прежние пятисекундные паузы CSS/JS/шрифтов исчезли; снятие HTTP403
  или доступ к личному кабинету не утверждается.
- Core/firewall running, основной selector `proxy-active`, доступно 144164 KiB
  памяти, memory warnings отсутствуют; state/config mode0600.
- Router E2E завершён с `router e2e ok`; повторный DNS-запрос с роутера к
  `192.168.1.1` вернул реальный адрес Wildberries, диагностические listeners/NAT
  отсутствуют.

Закрытый шестифайловый комплект до применения:
`/opt/etc/hincyray/rollback-dns-whitelist-20261003-080058-16486` (mode0700).
В него входят бинарник, state, quality history, generated config и обе private
настройки уведомлений/автоматизации. Это снимок перед изменением DNS без
остановки daemon, не комплект обновления бинарника. Для отката только DNS
предпочтительны прежние DNS-поля через API и повторное применение, чтобы
сохранить более новые независимые изменения состояния.

Локальные диагностические протоколы: `/tmp/opencode/dns-fix-apply.log`,
`/tmp/opencode/dns-fix-browser.log`, `/tmp/opencode/dns-fix-e2e.log`,
`/tmp/opencode/internet-findings.md`.
Временные диагностические NAT-исключения, ядра и их private каталоги удалены.
