# Keenetic VPN Client Roadmap

> v0.8.0 is shipped as the `hincyray` router daemon. See [`hincyray-v0.1-status.md`](hincyray-v0.1-status.md) for the implemented / validated / not-implemented snapshot, and [`hincyray-entware-install.md`](hincyray-entware-install.md) for the install runbook. The desktop `xray-vpn-test` is the diagnostics surface behind the `desktop` feature.

## Goal

Build a lightweight VPN/proxy client for Keenetic Homebrew routers, starting with Keenetic Giga KN-1012, using the current XrayVpnTest project as the parser, benchmark, and diagnostics foundation.

The desktop application is the diagnostics surface. The shipped router product is `hincyray` v0.8.0: a router-installed daemon with a web panel that accepts subscriptions and direct configs (VLESS, VMess, Trojan, Shadowsocks, Hysteria2), lets the user choose a server, exposes a local SOCKS listener through Mihomo (Meta), and routes a separate WiFi segment through Mihomo with transparent proxy (iptables NAT REDIRECT for TCP + mangle TPROXY for UDP) via Keenetic traffic policy connmarks. No tun2socks, no TUN device. Per-device/per-SSID policy routing remains post-MVP.

## Target Device

- Primary router: Keenetic Giga KN-1012.
- Runtime environment: Keenetic Homebrew / Entware-style userspace.
- Preferred implementation language: Rust, to minimize memory use and keep one codebase for parsing, scoring, API, and UI backend.
- Proxy core: Mihomo (Meta) single binary. Xray is desktop-only (diagnostics via `tester.rs`).

## User-Facing Requirements

- Web UI available from the router LAN.
- Paste/import subscriptions and direct profile links from providers that normally target Happ or Incy.
- Parse VLESS (Reality + xtls-rprx-vision), VMess, Trojan, Shadowsocks, Hysteria2, and Xray-style JSON configs.
- Show available servers with protocol, transport, country/name, latency, stability, speed, and last error.
- Allow manual server selection.
- Allow automatic server selection based on measured quality.
- Allow rules such as specific devices, SSIDs, domains, or IP ranges to use the proxy while other traffic remains direct.
- Support a dedicated Wi-Fi/network segment that exits through the selected VPN/proxy server.
- Keep main configuration in the web UI, not only in terminal config files.
- Expose logs and copyable error messages for debugging.

## Proposed Architecture

- `xray-vpn-test` desktop app remains the macOS diagnostics UI and test harness.
- Shared Rust library modules handle subscription loading, provider fallbacks, profile normalization, and quality scoring.
- A new router daemon manages state, subscriptions, selected profiles, generated core configs, process lifecycle, and routing rules.
- A small web UI talks to the daemon over local HTTP API.
- Mihomo (Meta) runs as the main execution core, spawned as `mihomo -f config.yaml -d geo_dir`. YAML config is generated by `src/mihomo_config.rs` with redir (TCP, port 10810) and tproxy (UDP, port 10811) listeners, sniffer, fake-ip DNS, QUIC block, and split routing. Protocol builders cover VLESS (Reality + xtls-rprx-vision), VMess, Trojan, Shadowsocks, Hysteria2.
- Xray is no longer the router core; it remains the desktop diagnostics engine behind `tester.rs` via `src/xray_config.rs`.

## Router Integration Questions

These were verified on the actual Keenetic Homebrew environment (KN-1012, aarch64, Entware). Resolved answers below:

- CPU architecture and available Rust target triple for KN-1012. RESOLVED: aarch64, target `aarch64-unknown-linux-gnu.2.27` via `cargo zigbuild`.
- Available init/service manager and persistent storage paths. RESOLVED: Entware `/opt/etc/hincyray/`, init via Entware service, ndm hook in `/opt/etc/ndm/netfilter.d/`.
- Whether `iptables`, `ip rule`, `ip route`, `nftables`, or Keenetic-specific routing hooks are available. RESOLVED: `iptables` nat + mangle tables with NAT REDIRECT and TPROXY; Keenetic RCI API for traffic policy connmarks; ndm hook script for firewall reload survival.
- How separate Wi-Fi/guest networks are exposed to Homebrew userspace. RESOLVED: `HincyRay-VPN` SSID on `192.168.2.0/24` created via `ndmc`; traffic on that subnet matched by connmark policy.
- Whether transparent proxying is reliable, or whether the first MVP should expose HTTP/SOCKS proxy and document router UI integration. RESOLVED: NAT REDIRECT + TPROXY transparent proxy is reliable and validated on KN-1012 (E2E with Pixel 6a); HTTP/SOCKS proxy also exposed.
- Whether Mihomo can run within available RAM/CPU limits under real traffic. RESOLVED: Mihomo single binary runs within KN-1012 limits.

## MVP Scope

- Cross-compile or build a small Rust daemon for Keenetic Homebrew. DONE — `cargo zigbuild` + patchelf pipeline.
- Package installable artifact from GitHub Releases. DONE — interactive atomic installer (`scripts/hincyray-install.sh`).
- Include or download a compatible Mihomo binary, depending on licensing and size constraints. DONE — auto-update downloads and installs Mihomo from GitHub Releases through the local SOCKS proxy.
- Provide web UI for subscription import, server list, manual selection, and benchmark run. DONE.
- Generate Mihomo config for the selected profile. DONE — `src/mihomo_config.rs` with protocol builders for VLESS/VMess/Trojan/Shadowsocks/Hysteria2.
- Start/stop/restart Mihomo from the daemon. DONE — `CoreManager`.
- Expose a local SOCKS/HTTP proxy endpoint on the router. DONE.
- Persist settings and benchmark history. DONE.

### Current MVP Status (HincyRay daemon)

The `hincyray` daemon is shipped at v0.8.0 as a separate binary, sharing `src/profiles.rs`, `src/scoring.rs`, and `src/mihomo_config.rs` with the desktop app. The desktop GUI (`xray-vpn-test`) remains the macOS diagnostics surface (feature `desktop`) and uses `src/xray_config.rs` + `src/tester.rs` locally.

The canonical v0.1 status (implemented, validated on KN-1012, not implemented, next milestones) lives in [`hincyray-v0.1-status.md`](hincyray-v0.1-status.md); the install runbook lives in [`hincyray-entware-install.md`](hincyray-entware-install.md). The implementation details below are kept here as a source-tree reference.

Implemented (v0.8.0 cumulative):

- `src/bin/hincyray.rs` binary entrypoint calling `xray_vpn_test::hincyray::run()`.
- `src/hincyray.rs` library module: sync `std::net::TcpListener` HTTP server, no async runtime, no web framework. One thread per connection, 15 s read/write timeouts, 1 MiB request body cap.
- Bind default `0.0.0.0:8088`, override via `HINCYRAY_LISTEN`.
- State path auto-detection: `HINCYRAY_STATE` env → `/opt/etc/hincyray/state.json` (Entware) → `/etc/hincyray/state.json` (OpenWrt) → `$HOME/.config/hincyray/state.json` → `./hincyray-state.json`. Atomic save via temp file + rename, corruption recovery (backup to `.corrupt`, log error).
- Mihomo config path: `HINCYRAY_MIHOMO_CONFIG` env → `config.yaml` next to state. Geo assets in a configurable `geo_dir` (must contain `geoip.metadb`; `geo-auto-update: false` to prevent MMDB download hang).
- JSON state: profiles (including `block_quic` per server), active_profile_id, auto_select, listen_host (default `127.0.0.1`), socks_port (default `10808`), http_port (default `10809`, reserved), mihomo_path, mihomo_config_path, metrics_history, routing_rules, split_routing settings, policy_name/policy_mark, quic_mode, tproxy_available, auto_bench_interval_hours, dns_settings, port routing, geo asset paths.
- HTTP API: `GET /`, `GET /api/health`, `GET /api/status`, `GET /api/profiles`, `POST /api/profiles/import`, `POST /api/profiles/block-quic`, `POST /api/active-profile`, `GET /api/mihomo-config`, `POST /api/core/start|stop|restart`, `GET|POST /api/bench/*`, `GET /api/stats`, `POST /api/favorites/toggle`, `GET /api/favorites`, `GET|POST /api/subscriptions/*`, `GET /api/routing`, `POST /api/routing/settings`, `POST /api/routing/rules`, `POST /api/routing/catalog/refresh`, `POST /api/routing/apply`, `GET /api/routing/firewall-status`, `POST /api/routing/firewall-start`, `POST /api/routing/firewall-stop`, `GET /api/logs`, `GET /api/system`, `GET|POST /api/auto-settings`, `GET /api/update/status`, `GET /api/update/check`, `POST /api/update/apply`, `GET|POST /api/update/settings`.
- `CoreManager` with one in-memory `Child`, status detection via `try_wait`, idempotent stop. Mihomo is spawned as `mihomo -f config.yaml -d geo_dir` with stdout+stderr redirected to a rotating log file (not `/dev/null`).
- `FirewallManager` installs iptables NAT REDIRECT (TCP, port 10810, nat table HINCYRAY chain) + mangle TPROXY (UDP, port 10811, mangle table HINCYRAY_UDP chain) matching Keenetic traffic policy connmarks. An ndm hook script (`/opt/etc/ndm/netfilter.d/hincyray.sh`) is auto-generated and re-runs after every ndm firewall reload. Kernel modules `xt_TPROXY`, `xt_socket`, `xt_comment` are loaded at startup. TPROXY unavailable → TCP-only REDIRECT + QUIC blocked. The watchdog is a safety net that reinstalls rules and reschedules core restart with exponential backoff.
- DNS is always enabled in router mode (fake-ip, listen `0.0.0.0:1053`) — the firewall unconditionally DNATs DNS to `127.0.0.1:1053`, so the Mihomo config must always include the DNS listener. `load_state()` forces `dns_settings.enabled=true` when split routing is on.
- Mihomo config generation via `src/mihomo_config.rs` (`build_mihomo_router_config`): redir + tproxy listeners, sniffer, fake-ip DNS, QUIC block, split routing. Protocol builders for VLESS (Reality + xtls-rprx-vision), VMess, Trojan, Shadowsocks, Hysteria2. 17 tests in the module.
- Keenetic RCI API integration (`localhost:79/rci/show/ip/policy`) queries policy connmark for dynamic VPN bridge resolution (not hardcoded `br1`).
- Watchdog always runs (not just split routing): core restart with exponential backoff + firewall rule reinstall + auto-update scheduling. Health-check failover via SOCKS probe: 3 consecutive failures → switch to next-best profile by score. Auto-benchmark scheduling (`auto_bench_interval_hours`) with auto-select best profile after benchmark.
- Mihomo auto-update: `get_mihomo_version()`, `is_newer_version()`, `check_latest_mihomo_release()` (GitHub API through the local SOCKS proxy), `download_and_install_mihomo()` (download `.gz` through proxy, gunzip, verify, unlink+copy to avoid ETXTBSY, backup `.bak`, rollback on failure). Requires the core to be running (GitHub API requests go through the SOCKS proxy). API endpoints: `/api/update/status`, `/api/update/check`, `/api/update/apply`, `/api/update/settings`.
- System monitoring (`GET /api/system`): CPU model/cores/features/temp/usage per-core, RAM total/free/available/usage, load average, uptime, kernel, hostname, model via `/proc` + `/sys`. `CpuTimes` delta computation stored in `DaemonInner`.
- Graceful shutdown via SIGTERM/SIGINT (stops children, cleans iptables, persists state).
- Web UI: index page, profiles/subscriptions/benchmark, routing settings + rules catalog, firewall status, Mihomo Update section, system monitoring (progress bars auto-refreshed every 5s), logs viewer, auto-settings, auto-refresh status every 5s.
- The daemon can be built without the desktop feature: `cargo build --release --no-default-features --bin hincyray` skips `eframe`/`egui_extras`/`arboard` so the Entware/OpenWrt artifact stays small and free of GUI dependencies. Shared modules (`profiles`, `scoring`, `mihomo_config`, `hincyray`) remain available; `app`/`theme`/`run()` are gated behind the `desktop` feature.
- Cross-compilation pipeline: `cargo zigbuild --release --no-default-features --bin hincyray --target aarch64-unknown-linux-gnu.2.27` + patchelf `--set-interpreter /opt/lib/ld-linux-aarch64.so.1 --set-rpath /opt/lib`.
- Interactive atomic installer script (`scripts/hincyray-install.sh`, archinstall-style: staging → backup → atomic `mv` → verify → commit/rollback). Checks for kernel modules (xt_TPROXY, xt_socket, xt_comment) and ndm hook directory.
- WiFi VPN segment: `scripts/wifi-segment-setup.sh` creates the `HincyRay-VPN` SSID on `192.168.2.0/24` via Keenetic `ndmc`. Transparent proxy routes traffic on this segment through Mihomo via NAT REDIRECT + TPROXY. Validated on KN-1012 with E2E testing (Pixel 6a on HincyRay-VPN WiFi); 5 transparent proxy bugs fixed.
- 136 tests total across the crate.

Not yet implemented (post-MVP, tracked below):

- Per-device / per-SSID rules: the daemon manages per-subnet WiFi routing and per-domain / per-IP / per-service split rules, but per-client and per-SSID policy routing remain pending.
- Export/import full router-client configuration.
- Full web UI polish beyond the current sections (an endpoint-listing index plus the sections above are shipped).

## Post-MVP Scope

- Automatic server selector: DONE — auto-select runs after benchmark using `scoring::quality_score`; health-check failover switches to the next-best profile after 3 consecutive SOCKS probe failures.
- Policy routing for selected clients, SSIDs, domains, or IP ranges: per-subnet WiFi routing (transparent proxy via NAT REDIRECT + TPROXY) and per-domain/per-IP/per-service split rules are shipped. Per-client/per-SSID rules remain.
- Health checks with automatic failover: DONE — SOCKS probe, 3 consecutive failures → switch to next-best profile by score.
- Export/import full router-client configuration: still pending.
- Mihomo advanced rule-based routing: adopted — Mihomo (Meta) is now the single core, with rule engine, split routing, and sniffer in use.

## Non-Goals For The First Router MVP

- Full replacement of every Happ/Incy feature.
- Kernel-level VPN implementation.
- Complex terminal-only Mihomo workflows as the primary UX.
- Supporting every router model before KN-1012 is validated.

## Development Strategy

1. Keep all current parsing and benchmarking tests passing on macOS.
2. Refactor shared parser/scoring code only when needed by the router daemon.
3. Build the router daemon and API as a separate binary, not by overloading the desktop UI.
4. Validate Mihomo config generation on macOS first, then on Keenetic.
5. Add router routing features incrementally after a local proxy MVP works reliably.
