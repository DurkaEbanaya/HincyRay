## Steam memory incident (read-only evidence)

During a Steam download, Mihomo RSS reached 190972 KiB, MemAvailable fell to approximately 64156 KiB, and the memory guard warning threshold was exceeded. Steam cache connections from LAN `192.168.1.95` matched `GeoSite(steam)` and a pinned group selecting REJECT; logs showed repeated new attempts while some other VPN paths remained active. After load fell, Mihomo RSS stayed around 163–168 MiB; after a user-initiated core restart it was approximately 80 MiB and MemAvailable rose to approximately 187 MiB. This establishes substantial pressure and that a restart releases memory, but does not distinguish retained Go heap, cached data, live connection buffers, upstream behavior, or an unbounded leak. The memory guard is observational; there is no automatic recovery policy in this release. No deliberate load reproduction was performed. Private read-only capture: `/home/lain/steam-memory-{snapshot,connections,logs,trend,late}.log`.

Possible next measurements are bounded Mihomo heap/pprof snapshots if the controller supports them, sampled per-route connections plus RSS/FD/CPU/Go heap before/during/after natural load, and retry-rate correlation. Changes to Steam routing or an automatic restart policy require evidence and a separate rollback-tested design; `GOMEMLIMIT` alone is not an RSS cap.

Steam's repeated attempts against a pinned REJECT path may increase churn; it is not proof that those attempts alone retained the heap. Before considering a routing change, inspect the exact rule and fallback leaf at the incident time. If the user wants this workload separated, an explicit DIRECT or independently tested VPN target can be evaluated with its WAN-exposure tradeoff. A future protective restart would need sustained memory plus controller/forwarding evidence, cooldown, and selector preservation: restarting on one RSS sample risks interrupting healthy traffic without addressing the cause.
