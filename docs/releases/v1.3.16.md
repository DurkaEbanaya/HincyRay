# HincyRay v1.3.16

Date: `2026-09-21`.

This release fixes a cross-VPN outage caused by one Mihomo health timeout under load. GitHub commit, push, and release remain pending and unauthorized.

## Incident

- PC `192.168.2.33` downloaded from `us.aws.cdn.hf.co` through a rule targeting profile 202. The pinned profile was already unhealthy, so its group used shared `proxy-active` rather than the intended German outbound.
- The parallel transfer loaded that same active VPN. A shared health request crossed the generated 3000 ms deadline; Mihomo immediately wrote the active proxy unhealthy and the canonical v1.3.15 fallback selected REJECT for every new VPN-routed connection.
- Explicit DIRECT remained available by policy. Mihomo stayed alive and emitted `proxy[REJECT]`; firewall, DNS, REDIRECT, TPROXY, memory, file descriptors, and conntrack were healthy. This was not a core crash or WAN leak.
- Recovery samples repeatedly clustered at 3070-3101 ms, immediately above the old timeout. No intentional saturation reproduction was performed.

## Fix

- Canonical `proxy` is a selector `[proxy-active, REJECT]`. A hidden `proxy-health` fallback owns the main health probe but cannot select the dataplane itself.
- Main health uses its own exact URL key, an 8-second timeout, and a 10-second interval. Pinned and Parovozik groups use unique URL namespaces at 60-second intervals.
- The daemon reads one `/proxies` snapshot under the apply lock and counts only fresh main-namespace samples. Three failed samples select REJECT; two successful samples restore the active VPN. Duplicate polls do not count.
- Samples are scoped to core generation and canonical active lifecycle identity. Explicit successful profile changes baseline the new health sample; stale history cannot penalize a replacement profile.
- Selector intent survives hot reload, process restart, failed activation rollback, and manual or automatic Mihomo updates. Exact selector shape is validated after readiness; an unverifiable runtime is stopped fail-closed.
- VPN groups contain no DIRECT fallback. User-selected DIRECT rules and other explicit direct policy remain unchanged.
