## Scope

- One wide searchable grouped server picker is used by rule creation, inline rule editing, connection actions, and the connection rule editor. Entries include profile IDs and Dead Servers/fallback state.
- `POST /api/routing/resource-reload` applies serialized desired routing before closing matching connections. Domain matching includes sniffed host; source IP, destination port, and network qualifiers are preserved.
- Dead target intent remains saved while runtime fallback to the active VPN is explicit. GeoIP, GeoSite, and rule-set candidates are identified as runtime Mihomo decisions.
- Connection closure is capped at 20 IDs and returns at most 20 redacted 512-byte errors.
- Routing mutations use a shared apply boundary. Persistence failures restore in-memory state, and device-route apply starts the core before transparent routing is enabled.
- VLESS `pcs` certificate pins map to Mihomo `fingerprint`, with optional single-name `vcn` mapped to `name-cert-verify`. One SHA-256 pin is strictly validated; TLS verification is not disabled.

## Certificate-Pin Incident

The reported broad profile failure was not caused by the routing picker. Isolated temporary-core tests kept active profile 88 and the persistent core unchanged. BeautifulVPN `Obhod 11` retained the exact pre-incident connection identity but failed on an upstream certificate-name mismatch. Removing VLESS `packet-encoding: xudp` did not change that result.

Quattro `LTE 86 Italy` had been replaced by a subscription refresh: its old and current raw identities differed. Both strict current probes initially failed because HincyRay ignored the Xray share-link `pcs` field. The current catalog contains 301 VLESS profiles with one valid colon-separated SHA-256 `pcs` pin. Xray defines `pcs` as `pinnedPeerCertSha256`; Mihomo implements the same safe certificate pin through `fingerprint`. The fix maps one strictly validated 64-hex or colon-separated SHA-256 pin and optional one-name `vcn`, without setting `skip-cert-verify`.

Before deployment, an isolated generated config contained `fingerprint`, omitted `skip-cert-verify`, passed installed Mihomo validation, and returned HTTP 200 through current LTE 86. After deployment, the ordinary daemon benchmark passed LTE 86 with 359 ms latency and 0% loss. A real active-profile switch then selected LTE 86, kept core running, and reported `proxy-active` alive at 92 ms; the transaction subsequently restored profile 88 with core/firewall running. The old pre-refresh LTE 86 identity still returned upstream TLS access denied even with a diagnostic insecure temporary config, so restoring the old subscription payload was neither necessary nor a repair.

Normalized durable projections matched the rollback snapshot: active profile, profile ID order, the set of all 519 canonical v2 Dead Servers refs, promoted timestamps, favorites, routing rules, server route registry, device routes, split-routing settings, and quality history. Dead-ref serialization order changed, but membership did not: before/after counts are both 519 v2, with zero added or removed refs.
