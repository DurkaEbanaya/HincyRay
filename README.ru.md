# HincyRay v1.3.30

v1.3.30 расширяет «Лучшие из лучших» до 16 серверов с поиском, ручными профилями и явным добавлением/удалением. Маршрут сохраняет рабочий сервер и блокирует трафик до проверки новой цели при отказе. Оба списка целей сортируются по свежим проверкам сервисов и proxy ping. См. [запись релиза](docs/releases/v1.3.30.md). Интеграции Jitsi в этой версии нет.

Бинарник Keenetic/Entware aarch64: [GitHub Release v1.3.30](https://github.com/DurkaEbanaya/HincyRay/releases/tag/v1.3.30). SHA256: `5fd5a6989fb9339414394dddcfdf27ed93e9d5337bf16e6d4d53ad534d4b9bec`. Упоминания запрета или ожидания публикации ниже относятся к историческим версиям, а не к этому релизу.

---

HincyRay — лёгкий VPN/proxy-клиент для роутеров Keenetic. Поставляет роутер-демон (`hincyray`), который переиспользует парсер и benchmark engine из десктопного инструмента `XrayVpnTest`, и предоставляет встроенную веб-панель в локальной сети роутера.

Демон использует **Mihomo (Clash.Meta)** как единое прокси-ядро, поддерживая VLESS (Reality/xhttp), VMess, Trojan, Shadowsocks, ShadowsocksR, Snell, HTTP, SOCKS, AnyTLS, Hysteria v1/v2 (port hopping), WireGuard, TUIC, SSH, MASQUE, OpenVPN и Tailscale. Transparent proxying через iptables NAT REDIRECT (TCP) + TPROXY (UDP) — без tun2socks, без TUN-устройства.

## Как это работает

v1.3.12 является проверенным и развёрнутым локальным исправлением: явные действия **Проверить сервисы** проверяют YouTube, Telegram и AI Studio в выбранной области вместо наследования глобального Find N/short-circuit. Все итоговые проверки пройдены (674 Rust / 88 browser-тестов / 131 frontend-маршрут). Реальный полный тест активного профиля 88 прошёл все три сервиса; read-only live Chromium подтвердил его зелёные индикаторы и прежние красные результаты профиля 431. [Превью YouTube](docs/youtube-availability.md) остаются contract 1, не воспроизведением видео или здоровьем Mihomo.

Итоговые артефакт, rollback, router E2E, service smoke и live UI: [запись v1.3.12](docs/releases/v1.3.12.md). История v1.3.7-v1.3.11 сохранена без изменений. Публикация GitHub ожидается и не разрешена; доступность ресурса v1.3.12 не заявляется. `HINCYRAY_BIN_PATH` остаётся путём офлайн-артефакта.

```
Устройство на Keenetic-политике "HincyRay"
         |
         v
  iptables nat PREROUTING
  (матч по policy connmark)
         |
    +----+----+
    v         v
  TCP       UDP
    |         |
  REDIRECT  TPROXY
  ->10810   ->10811
    |         |
    v         v
  Mihomo redir/tproxy inbounds
  (redir-in TCP 10810, tproxy-in UDP 10811)
         |
         v
  Активный outbound (VLESS/VMess/Trojan/SS/Hy2/WG/TUIC)
         |
         v
  Интернет
```

Устройства, не назначенные на политику, используют обычный маршрут — основная сеть не затрагивается.

### Выживание при ndm firewall reload

Демон `ndm` в Keenetic пересоздаёт все iptables chains при изменениях конфигурации, событиях WAN и обновлении DHCP. HincyRay устанавливает hook-скрипт в `/opt/etc/ndm/netfilter.d/hincyray.sh`, который **ndm вызывает сам** после каждой перезагрузки firewall, переустанавливая все правила атомарно. Watchdog каждые 10 секунд — запасная страховка.

## Возможности

### v1.3.24

В карточках статуса появилась проверка «Доступность Direct». Она параллельно выполняет ограниченные прямые запросы без SOCKS/HTTP proxy к Google, VK, ya.ru и YouTube и показывает отдельный зелёный или красный результат для каждого сайта.

### v1.3.23

При первом открытии таблица профилей сразу показывает порядок «По результатам». Выбранный порядок, включая вручную указанный «Порядок импорта», сохраняется после перезагрузки страницы. Принятый запуск проверки сервисов подписки выбирает и запоминает «По результатам», поэтому повторное открытие не возвращает случайный на вид исходный порядок.

### v1.3.22

После принятого запуска «Проверить сервисы» для подписки список переключается на «По результатам». Внутри подписки выше серверы с большим числом успешных проверок превью YouTube, Telegram и AI; при равенстве используется ping свежей проверки. Непроверенные/устаревшие и недоступные серверы различаются, а колонка Ping показывает задержку, по которой выполняется сортировка.

### v1.3.21

Соединения Torrent SOCKS5 помечаются в обеих таблицах. Смена цели Torrent SOCKS5 переподключает только его потоки; применение общих правил переподключает существующие соединения, чтобы они получили новый маршрут. О неполном переподключении интерфейс сообщает явно.

### v1.3.20

В карточке Torrent SOCKS5 показан счётчик байт пароля. Пустое поле «Новый пароль» сохраняет только ранее настроенный пароль; пустой или слишком короткий первый пароль отклоняется до отправки настроек на роутер.

### v1.3.19

Torrent SOCKS5 можно включить при выключенной авторизации веб-панели; её также можно отключить, не выключая уже настроенный SOCKS5. Отдельные учётные данные SOCKS5 остаются обязательными.

### v1.3.18

Выбор серверов для правил, подключений и Torrent SOCKS открывается в центрированном окне с поиском. Автообновление откладывается на время редактирования, для удаления правила есть заметная кнопка и восстановление; правила выключенного Паровозика скрыты, список вагонов свёрнут. Инцидент роста памяти при загрузке Steam и пределы имеющихся данных описаны отдельно; автоматическое восстановление памяти не включалось.

### v1.3.17

Торрент-клиент может использовать отдельный authenticated SOCKS5 listener, чья identity маршрутизируется независимо от доменов, портов и зашифрованного BitTorrent payload. TCP и поддерживаемый клиентом SOCKS5 UDP работают через один listener в существующем процессе Mihomo; смена target не требует перенастройки клиента. API и config preview не возвращают credentials, а изменения listener/state проходят validation и transactional rollback.

### v1.3.16

Canonical dataplane `proxy` теперь selector над `proxy-active` и `REJECT`; скрытый изолированный sensor измеряет active VPN, но не меняет routing напрямую. Watchdog считает только свежие URL-specific samples, использует hysteresis три отказа/два успеха, сохраняет fail-closed state при reload, restart, update и rollback и изолирует более редкие namespaces pinned/Parovozik. Поэтому насыщенная pinned-загрузка больше не превращает одну задержанную трёхсекундную пробу в мгновенный общий VPN outage.

### v1.3.15

Canonical active, pinned-server, exact-current-server и Parovozik VPN groups ставят `REJECT` первым. Mihomo пропускает его, пока VPN-участник здоров, но при своём all-unhealthy поведении выбирает первый элемент и теперь отклоняет соединение локально вместо выхода через WAN или повторных подключений к мёртвому upstream. Диагностика задержки тестирует raw active outbound и не отравляет aggregate group state; UI консервативно показывает rejected chains и неизвестное здоровье.

### v1.3.14

Выбор routing target теперь использует общий широкий searchable picker для новых и существующих правил и действий Connections. Записи показывают ID профиля, длинные имена без обрезания и состояние Dead Servers/fallback. Пока picker открыт, polling таблицы соединений приостанавливается.

Typed resource-reload сериализует изменение конфигурации, применяет desired routing, затем закрывает совпадающие Mihomo-соединения по sniffed host или destination IP с учётом source, port и network. Закрытие ограничено, ошибки редактируются. GeoIP, GeoSite и rule-set остаются runtime-решениями Mihomo, а не отображаются как достоверно выбранная цель. Ошибка persistence откатывает состояние в памяти; device-route apply сначала обеспечивает запущенное ядро и только затем прозрачную маршрутизацию.

### v1.3.13

Обычные действия отправляют `availability_full` с необязательной строгой политикой `service_checks`: упорядоченный префикс `youtube` (YT), `telegram` (YT+TG) либо `ai`/`all` (YT+TG+AI) и boolean `fail_fast`. Общие настройки GUI применяются ко всем областям; All и fail-fast доступны в обычном и расширенном режимах. Отсутствующая/null политика сохраняет прежнюю полную проверку всех сервисов. Обычная проверка не использует `search` или discovery preflight; цель Find N относится только к отдельному явному расширенному глобальному действию.

Явная обычная политика допускает ровно `min(requested workers, candidates)` либо возвращает HTTP 503 до резервирования, сохраняя существующее задание вместо молчаливого сокращения работников. Прежняя оценка 80 MiB резерва + 48 MiB/worker требует 272 MiB доступной памяти для четырёх; неизвестный/нулевой бюджет отклоняется. Legacy/adaptive caps и ограничение оставшейся целью сохранены. Thumbnail contract 1 больше не ждёт native YouTube mutex: у каждого работника приватные core/config/captures, ограниченный decoder и cancellation guards. Native playback contract 7 и общая Telegram SQLite session остаются сериализованными. Четыре реальных одновременных успешных router transfer пока не доказаны; нативное видео, новая авторизация/runtime, generic health и автоматические lifecycle-действия не добавлены.

Живой запрос четырёх кандидатов отклонён до резервирования: память допускала троих, прежнее idle-задание сохранено. Последующий обычный `availability_full` для `[88]`, concurrency четыре и явной YT/no-fail-fast политики допустил ровно одного работника для одного кандидата (не сокращение четырёхкандидатной проверки из-за памяти), без search/preflight. Contract-1 превью прошли одну попытку; TG/AI не запрашивались и не стали ложными зелёными успехами. Durable lifecycle и desired routing/settings projections не изменились; cache/stats/traffic могут обновляться ожидаемо. Отдельный реальный desktop/mobile DOM подтвердил доступные All/fail-fast, зелёный/current YT и серые/skipped TG/AI на 88, свёрнутые технические детали, отсутствие sidebar clutter, mobile overflow и JS-ошибок. Перехваченные single/global builders получили mock 503 без пересылки mutations; новые положительные All/TG/AI результаты v1.3.13 и динамические fail-fast последовательности пока не проверены. Полные сервисные/live UI свидетельства ниже исторические.

Нативное воспроизведение видео, автоматические quality/Dead Servers/AutoSelect действия, количественное ускорение или побайтовая изоляция всего состояния не заявляются. ### v1.3.10

Все области пользовательского поиска используют **страницу и превью YouTube**: подтверждение публичного канала MrBeast и успешную загрузку/декодирование превью трёх разных видео. Новые методы `availability_quick`/`availability_full` и результаты `search_availability` используют `youtube_thumbnails` contract 1. Общие политики завершения/отказов и префиксы Find N сохраняются; альтернативная YouTube-проверка в поиске не предлагается.

Этот метод не делает Innertube-запросов, не загружает видео, не импортирует cookies/session, не выполняет JavaScript и не обходит авторизацию. Успех означает только доступность страницы/изображений, а не воспроизведение или доступ к аккаунту. Нативные contract-7 `quick`/`full` API/история остаются отдельно ради уже поставленного API и сохранённых данных. Availability сохраняет ресурсную диагностику, не generic EWMA health или общий нативный успех, и не запускает подъём профилей, автоматические Dead Servers или AutoSelect.

Все итоговые проверки версии пройдены (668 Rust / 67 browser-тестов / 131 UI-маршрут); развёртывание с подтверждённым SHA прошло router E2E. Живой поиск с целью 1 на активном профиле 88 подтвердил канал MrBeast и три разных декодированных превью, достиг цели без отмены и сохранил активную идентичность, порядок и Dead Servers. Ресурсная диагностика, учёт поиска и фоновый учёт трафика могут меняться; побайтовая неизменность всего состояния, количественное ускорение или сравнение стоимости трафика не заявляются. Подробности: [границы и свидетельства](docs/youtube-availability.md), [`CHANGELOG.md`](CHANGELOG.md) и [`docs/releases/v1.3.10.md`](docs/releases/v1.3.10.md).

### v1.3.9

v1.3.9 принимает завершённый HTTPS-ответ с любым HTTP-статусом 200-599 как свидетельство транспортной доступности для адаптивной предпроверки, повторяя запрос один раз на другом домене через тот же изолированный Mihomo core. Это не успешная проверка YouTube. Приватные файлы core сохраняются до завершения и reap дочернего процесса; status хранит не более 20 диагностик предпроверки с очищенными от секретов ошибками до 2 KiB без штрафов здоровью или Dead Servers.

Нативная проверка YouTube использует прямой VISIONOS Innertube без обязательного web watch/bootstrap и JavaScript runtime. Успех требует успешной передачи не менее 16 KiB медиаданных с video MIME. Bot/login-отказ, HTTP 429 и отказ совместимости клиента являются **неопределёнными**: UI показывает amber/unknown, сводка не превращает unknown или устаревшие результаты в успех/отказ, а неопределённые свидетельства не запускают подъём профилей, Dead Servers или AutoSelect. Неопределённая история остаётся такой; native resource contract 7 делает свидетельства contract 6 устаревшими, а поле `inconclusive` с serde default допускает старые сохранения.

Linux core теперь запускается через постоянный ограниченный owner-thread: завершение HTTP-потока не вызывает Mihomo `PDEATHSIG`; очистка при смерти демона и владение дочерним процессом сохранены. Все обязательные проверки пройдены (649 Rust / 66 browser-тестов / 131 UI-маршрут), развёртывание с подтверждённым SHA прошло router E2E. Живая диагностика сохранила bot-отказ как unknown, не нашла успешного сервера и не изменила активную идентичность, порядок профилей или Dead Servers. Разрешённая ручная коррекция времени не устранила bot-отказ и TLS EOF другого кандидата. NTP сначала не был синхронизирован, затем независимый аудит дважды подтвердил accurate/synchronized через `pool.ntp.org` в 17:34 UTC с расхождением относительно хоста в одну секунду; сохранение после перезагрузки не проверено.

Анонимные медиабайты, исправленное воспроизведение, ложность всех прежних отказов или количественное ускорение не заявляются. Импорт cookies/session, обход авторизации, captcha, JavaScript и yt-dlp runtime не добавляются. - **Интерактивный атомарный установщик**: `scripts/hincyray-install.sh`.

### v0.1–v0.5

- **Поддержка протоколов**: VLESS (Reality/TLS/xhttp), VMess (base64-JSON, WS/gRPC/TCP), Trojan, Shadowsocks, Hysteria2, WireGuard, TUIC.
- **HWID-фингерпринт**: настраиваемая идентификация устройства для запросов подписок Happ.
- **Защита от утечек DNS**: удалённые DNS через прокси, локальные DNS для прямых доменов.
- **Портовый роутинг**: режимы all / allow_list / deny_list.
- **GeoIP/GeoSite**: настраиваемый путь к geo-ассетам.
- **WiFi traffic split**: правила матчат geosite, домены, IP/CIDR, geoip, порты, тип сети.
- **Бенчмарк/статы/избранное/подписки**: методы TCP/HEAD/GET, метрики по профилям, обновление подписок.

## Установка

Используйте интерактивный атомарный установщик:

```bash
sh scripts/hincyray-install.sh
```

Установщик проверяет kernel modules, создаёт директорию ndm hook, устанавливает бинарник, init-скрипт и состояние по умолчанию. Staging → backup → atomic `mv` → verify → commit/rollback.

Для публичного релиза установщик скачивает точный asset `hincyray` из GitHub Releases, если локальный бинарник отсутствует. Для offline-установки по-прежнему можно скопировать бинарник в `/tmp/hincyray` или задать `HINCYRAY_BIN_PATH`.

См. [`docs/hincyray-entware-install.md`](docs/hincyray-entware-install.md) для ручной установки.

## Веб-панель

```
http://<ip-роутера>:8088/
```

Встроенная Fluent/Acrylic-панель с RU/EN i18n, светлой/тёмной темой и навигацией для desktop, tablet и mobile. Профили занимают доступную ширину на ПК и планшетах в адаптивной многоколоночной раскладке; mobile остаётся одноколоночным. Длительные тесты, загрузки и apply-операции показывают движущийся индикатор активности. Статус, профили, benchmark, импорт, подписки, routing, firewall, DNS, диагностика, backup, HWID, системный мониторинг, управление Mihomo, трафик, соединения и логи доступны без внешнего CDN и frontend build step. Вместо периодического полного refresh используются лёгкие heartbeat статуса и системы.

## WiFi VPN-сегмент (опционально)

- `scripts/wifi-segment-setup.sh` — создаёт SSID `HincyRay-VPN` на `192.168.2.0/24` через Keenetic `ndmc`.
- Назначьте каждое устройство, которое должно идти через VPN, на Keenetic traffic policy "HincyRay". **Одного SSID/подсети недостаточно**: HincyRay матчит пакеты по policy connmark.
- Демон управляет всем transparent proxying через `FirewallManager`:
  1. Запрашивает connmark политики через Keenetic RCI API.
  2. Устанавливает iptables nat HINCYRAY chain (TCP REDIRECT на порт 10810) по connmark.
  3. Устанавливает iptables mangle HINCYRAY_UDP chain (UDP TPROXY на порт 10811) если TPROXY доступен.
  4. Устанавливает DNS DNAT-правила (порт 53 → 127.0.0.1:1053).
  5. Генерирует ndm hook-скрипт для выживания при firewall reload.
  6. Watchdog переустанавливает правила при отсутствии.

### Per-device routing

Устройства, назначенные на политику HincyRay, могут индивидуально маршрутизироваться на другую цель (DIRECT, активный прокси или конкретный профиль). Правила добавляются как `SRC-IP-CIDR,<ip>/32,<target>` перед общими правилами роутинга, обеспечивая приоритет правил для конкретных устройств.

Используйте секцию "Per-Device Routing" в веб-панели:
1. Нажмите "Scan devices (ARP)" для обнаружения устройств LAN.
2. Добавьте маршрут: выберите IP устройства, имя и цель.
3. Нажмите "Apply Mihomo config" для активации.
